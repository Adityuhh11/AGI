## Reading the baseline

First measurement on the real model (GPU, bf16), recorded before any retrieval tuning. 38 queries written by Claude from the actual files in `Sample Data/`.

- **Strong:** exact names (queries 18-21 all rank 1), project documentation, and PDFs (5 of 6 at rank 1; the t-table page, which has almost no extractable text, is found at rank 1 through its page image). No forbidden file surfaced, including `JWT_ACCESS_SECRET` (query 26).
- **Weakest group: images (queries 33, 35, 36, 37, 38).** A diagnostic run showed the vector side alone ranks the right image at 1 or 2 for all five queries (cosine 0.77-0.80). Fusion then demotes them: an image chunk's keyword text is only its file name, so it appears in one ranking while text chunks that match on both sides sum two reciprocal-rank terms. The cause is the fusion rule, not the embedding model. Phase 6 candidates: weight or per-kind pools, or let a strong vector-only match survive fusion.
- **Small or near-duplicate code files:** `asynchandler.js` (237 bytes) at rank 7, `SearchBar.jsx` at 6, `ProtectedRoute.jsx` at 3 behind the similar `GuestRoute.jsx`, `ForgotPassword.jsx` at 3. Tiny files carry little text to embed; this group is a candidate for tree-sitter chunking and a reranker.
- **Expectation corrected during the first run:** the query "contribution guidelines" expected `Documentation/CONTRIBUTING.md`, which is a 0-byte file with nothing to find. It was replaced by a question about the README's AI-usage section. No other expectation or any retrieval parameter was changed.
