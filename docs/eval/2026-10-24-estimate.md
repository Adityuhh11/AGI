# Estimating how long indexing takes (2026-10-24)

`internal/estimate` turns a survey of a folder (files and bytes by kind, from the engine's `POST /survey`, which opens no file) and the
choices made into a time, so the setup guide and the File search page can say "about 25 min" before anything is indexed. This records
where its numbers come from and how far off it was.

Machine: i5-13420H, RTX 4050 Laptop (Vulkan), llama.cpp b11719, real model. Timings are `Indexer.sync` straight into a fresh store, so
no pacing: the speed Fast. The launcher's own engine was running beside them.

## The model

time = (text chunks / text rate + pictures x picture time + files x 0.03 s + video seeks x 0.4 s) x speed factor

| Quantity | Value | From |
|---|---|---|
| text rate | 53 chunks/s on a card, 1.4 on the processor | `2026-10-20-indexing-choices.md` |
| picture time | 0.16 s on a card, 4.9 s on the processor (a picture, a PDF page, a video frame) | same |
| per file | 0.03 s | fit: Sample Data's 16.5 s less its embedding time, over 96 files |
| speed factor | 1, 1.9, 5.9 (fast, balanced, gentle) | `2026-10-18-pace.md` |
| code, Markdown, text | 1,086 / 829 / 1,691 bytes per chunk, at least one a file | the owner's index (below) |
| PDF | 15.9 text chunks per MB; pictures per MB: 17.7 every page, 8.8 `auto`, 0 words only | same |
| photo | 1 picture, or 1 text chunk (its name) | the engine |
| video | 1 text chunk (its name); with frames also 8 pictures | the engine |

The per-kind numbers come from the owner's real index (3,795 files, 2.2 GB, read-only from `meta.db`): code 7,806 chunks from 8.5 MB, Markdown
4,260 from 3.5 MB, text 2,819 from 4.8 MB, PDF 15,024 text chunks and 8,276 page pictures from 944 MB, 960 images, 17 videos with 136 frames.
Single PDFs vary enormously (median 6 pages, mean 28), so a PDF is scaled by its size, which is right in total.

## How far off it was

Predicted against measured, with the speed Fast:

| Folder, choices, device | Predicted | Took | Off |
|---|---|---|---|
| Sample Data (96 files), defaults, card | 14 s | 16.5 s | -15% |
| Sample Data, words only and names, card | 9 s | 8.0 s | +13% |
| Sample Data, defaults, processor | 6 min 21 s | 7 min 46 s | -18% |
| Sample Data, words only and names, processor | 3 min 39 s | 4 min 52 s | -25% |
| The owner's Documents folder (415 files, 120 PDFs), defaults, card | 3 min 53 s | 4 min 24 s | -12% |

The last row was not used to fit anything. It predicted 3,913 text chunks (3,359 made) and 915 pictures (981 made). On Sample Data the chunks were
underestimated by 32% (277 against 405): its code is in short files with short lines, so it makes one chunk per 755 bytes, not per 1,086. The
processor timings are the sample folder indexed with the model forced onto it (`2026-10-24` run, `docs/PERFORMANCE.md`).

So: within about a quarter, mostly low. That is what "about" means here. Once indexing runs, the time left it reports takes over (U1): in the live
run of the setup guide on this folder at Balanced it said 4 minutes left after 45 seconds (64 of 416 files). That is a different instrument,
files done over time, and it moves as the heavy files come; it was not compared with the end of that run.

## What it does not know

- A corpus unlike the owner's: bytes per chunk move with line length (755 here against 1,086), and PDF pages with PDF size.
- Another graphics card or processor: the rates are one laptop's. A machine twice as slow is twice as long.
- A survey counts files, not pages: the PDF numbers are averages, and a folder of three 400-page books is off by a lot in either direction.
- Cloud-only files (OneDrive) are counted by the size Windows reports and read when indexing starts.

## Reproduce

`internal/estimate/estimate_test.go` pins the four Sample Data timings to within a third. The Documents run:
`uv run python real_time.py "<folder>"` over `Indexer.sync` with `LlamaEmbedder` (not kept; it is the script `eval/runner.py` builds on), with
`AGI_LLAMA_SERVER` and `AGI_MODEL_DIR` set; its prediction from the `/survey` counts of the same folder.
